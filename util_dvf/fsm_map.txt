Key Architectural Shifts to Keep in Mind for util_dvf:
Payload Unpacking (-u): While runepkg extracts standard Debian ar/tar.xz payloads, util_dvf's unpacker has to handle RPM lead/header structures and extract compressed cpio payloads (gz, xz, zstd), which adds a bit of parser plumbing.

Integrity/Verification (-m / --verify): RPM relies heavily on built-in header digests and GPG signatures rather than standalone md5sum text manifests, so the verify command mirrors RPM's native integrity checks.

Got it. You want a clean architectural firewall separating stateless, read-only queries and text-out diagnostics (which don't need to touch the FSM at all) from state-changing transactions (which require full FSM rigor and rollback protections).

Here is the exact mapping of how to split your command functions to keep your code clean:

Group 1: Non-FSM Commands (Pure Text-Out, Local Queries, & Diagnostics)
These commands inspect existing data, print configuration settings, or rebuild local static indices. They do not modify system state or alter the package database, meaning zero FSM overhead is required.

Configuration & Path Printing:

--print-config (Outputs active paths/settings as text)

--print-config-file (Shows path to config file)

--print-pkglist-file (Shows autocomplete index paths)

--print-autopool (Dumps autocomplete pool contents)

Local Package Queries:

-l, --list [pattern] (Lists installed packages)

-s, --status <pkg> (Displays metadata for a specific installed package)

-L, --list-files <pkg> (Lists files owned by an installed package)

-S, --search <file-path> (Searches installed packages for a file match)

Remote Repository Queries:

search <pkg|pattern> (Queries local repo metadata cache for matching packages)

info <pkg> (Displays remote repository metadata)

Index Maintenance:

--rebuild-autocomplete (Rebuilds the memory-mapped binary name index)

--version / -h, --help (Displays CLI usage manual)

Group 2: FSM-Required Commands (State-Changing & Transactional)
These commands modify the filesystem, write to databases, resolve recursive dependencies, or alter system state. These must be routed through the FSM engine to guarantee atomicity and handle recovery if they fail halfway through.

Database & State Synchronization:

sync (Synchronizes host package database with system state)

update (Pulls and indexes remote repository metadata)

Installation & Removal:

-i, --install <rpm> (Resolves, downloads, stages, and installs packages)

-r, --remove <package-name> (Unlinks and purges an installed package)

upgrade (Batch downloads and installs system upgrades)

Staging & Building:

-u, --unpack <rpm> (Extracts payloads into build directories)

-b, --build [dir] [rpm] (Forges a new .rpm package)

download-only / download-depends (Touches the network and disk caches, benefiting from transactional tracking)

Why this split helps your code structure:
In your CLI dispatcher (util_dvf_cli.c), you can handle Group 1 directly in simple handler functions that print to stdout and exit 0.

For Group 2, the CLI dispatcher acts purely as a trigger that feeds arguments into util_dvf_fsm.c, letting the Finite State Machine take over the execution lifecycle (Resolving → Verifying → Executing → Committing).
